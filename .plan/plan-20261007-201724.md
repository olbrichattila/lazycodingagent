# Fix Linux Model Fetching HTTP Error and JSON Parsing

## Root Cause Analysis
On Linux/macOS, `TLlmClient` uses Free Pascal's `TFPHTTPClient` (whereas on Windows it uses `WinHTTP`). When fetching models or making API requests on Linux:
1. When an HTTP error or redirect occurs (e.g., HTTP 301/302/307/308 redirect, HTTP 401 Unauthorized, HTTP 403 Forbidden, HTTP 404 Not Found, or HTTP 429), `TFPHTTPClient` raises an `EHTTPClient` exception with a message like `'HTTP/1.1 301 Moved Permanently'` or `'HTTP/1.1 401 Unauthorized'` or does not automatically follow redirects by default unless `AllowRedirect := True` is set.
2. In `SendHttpGet` (and `SendHttpPost`), when an exception occurs or when `SendHttpGet` returns `False`, `ListModels` in `uLlmClient.pas` executes:
   ```pascal
   if SendHttpGet(Url, RespStr) then
     Result := ParseModelsResponse(RespStr)
   else begin
     Result := ParseModelsResponse(RespStr);
     if not Result.Success then begin
       if Result.ErrorMessage = '' then
         Result.ErrorMessage := RespStr;
     end;
     Result.Success := False;
   end;
   ```
   When `SendHttpGet` failed, `RespStr` contains the non-JSON error string (e.g. `'HTTP Error 301: ...'` or `'Connection Exception: HTTP/1.1 301 ...'`). `ListModels` still calls `ParseModelsResponse(RespStr)` on that plain text!
   `ParseModelsResponse` runs `GetJSON(AJsonStr)`, which throws:
   `JSON Parse Error: Error at line 1, Pos 4: Unexpected token (HTTP) encountered.`
   Because `Result.ErrorMessage` is then overwritten with this JSON parse error instead of the underlying HTTP error message, the user sees a misleading JSON syntax error.
3. Furthermore, `TFPHTTPClient` on Linux requires:
   - `AllowRedirect := True` (with reasonable `MaxRedirects`) to handle URL canonicalization and endpoints that redirect.
   - Proper `User-Agent` and header handling.
   - Clean handling of HTTP error status codes so response bodies from the server (which often contain real API error details in JSON or plain text) are captured without masking them behind a JSON parser crash.

## Proposed Changes

### 1. `uLlmClient.pas`
- **Configure `TFPHTTPClient` for Linux/macOS in both `SendHttpGet` and `SendHttpPost`**:
  - Set `Client.AllowRedirect := True;`
  - Set `Client.MaxRedirects := 5;`
  - Ensure standard `User-Agent: LazyCodingAgent/1.0` header is sent if not already set.
- **Fix error handling in `ListModels`**:
  - Do not unconditionally run `ParseModelsResponse` on `RespStr` when `SendHttpGet` returned `False`.
  - Only attempt `ParseModelsResponse(RespStr)` when `RespStr` looks like JSON (starts with `{` or `[` after trimming), and if parsing fails or returns empty error, retain the original HTTP status or connection error in `Result.ErrorMessage`.
- **Fix error handling in `SendChatCompletion`**:
  - Apply similar safeguard: if `SendHttpPost` fails and `RespStr` is not valid JSON, preserve the HTTP error string rather than letting JSON parser replace it with `"JSON Parse Error: Error at line 1, Pos 4..."`.
- **Improve `SendHttpGet` and `SendHttpPost` for `TFPHTTPClient`**:
  - Handle `EHTTPClient` exceptions gracefully so that any server response body stream is read before failing, extracting the HTTP status code and status text clearly.

### 2. Verification Plan
- Verify that `TFPHTTPClient` compiles cleanly with `AllowRedirect := True`.
- Test model listing logic for:
  - Valid endpoints (OpenRouter, OpenAI, Ollama, etc.).
  - Redirecting URLs (e.g. trailing slash redirect).
  - Invalid API key or HTTP error codes (e.g. 401/404) to ensure the actual HTTP / API error is reported to the user instead of "JSON Parse Error: Unexpected token (HTTP)".
