# LazyCodingAgent Workspace Layout Implementation Plan

## Goal

Replace the current empty `TForm1` scaffold with a modern, dark-first coding-agent workspace that supports:

- Main menu and toolbar
- A docked-by-default, detachable multi-window layout
- A persistent window-management menu for showing, hiding, docking, and restoring panels
- Drag rearrangement of docked panels
- A narrow icon navigation rail with tooltips
- Three initial workspace areas: navigation, reserved secondary panel, and the chat/agent workspace
- Home, Projects, Sessions, and Bots navigation entries
- Chat input with workspace context, Ask/Plan/Agent modes, and model selection
- Windows, Linux, and macOS compatibility through LCL APIs

The repository is currently only a Lazarus application shell: `mainunit.pas` contains an empty `TForm1`, `mainunit.lfm` contains only default form properties, and `lazycodingagent.lpi` includes only the main form unit. The implementation should therefore establish a small UI architecture rather than add all behavior to the form unit.

## Proposed layout

```text
+--------------------------------------------------------------------------------+
| Application menu | workspace title | ...                         [_][□][X]     |
+--------------------------------------------------------------------------------+
| Main toolbar: New | Open project | Save | Run/Ask | layout | theme | settings  |
+------+----------------------+----------------------------------+-----------------+
|      |                      |                                  |                 |
| Icon | Navigation panel     | Chat / Agent workspace            | Optional panel  |
| rail | (Home, Projects,     |                                  | (future)        |

+--------------------------------------------------------------------------------+
```

### Initial panel semantics

1. **Navigation rail**: fixed-width left strip containing icon buttons for Home, Projects, Sessions, and Bots. Every button must have a tooltip and accessible text. The selected item uses a strong accent background/indicator; icons should not be the only way to identify a command.
2. **Navigation content panel**: initially displays the selected section. It is docked to the main form by default and can be hidden or detached. This is the first full vertical panel.
3. **Secondary panel**: create a registered but initially blank/reserved dockable panel. It can later host instructions, project files, or context. It should have a visible title and empty-state text without committing to future content.
4. **Chat panel**: the primary workspace. Show the empty-state heading `What should we build in <project name>?`; use a safe fallback such as `your project` when no workspace is selected. Place the workspace name immediately above the composer. Place mode selectors and selected-model control in the composer footer, with **Agent** selected by default.
5. **Status bar**: expose current workspace, mode, model, and connection/agent state without duplicating the full toolbar.

## Architecture and files

Add focused units to keep responsibilities separate:

- `uAppTypes.pas`: shared enumerations and records such as navigation item, workspace mode (`Ask`, `Plan`, `Agent`), panel identifiers, panel visibility, and model display metadata. Keep these UI-independent where practical.
- `uTheme.pas`: dark/light palette, spacing, typography, control heights, and helper procedures for applying the selected theme. Avoid relying on platform-specific colors or Lazarus default visual styling. Provide a light palette from the same token set and persist only the preference, not hard-coded widget colors throughout the form.
- `uWorkspaceState.pas`: current workspace/project name, selected navigation item, selected mode, selected model, panel visibility, dock/floating state, and panel order. Add change notifications or an observer mechanism so the form and panels update consistently. Use stable panel IDs rather than control captions for persistence.
- `uDockPanel.pas`: a reusable panel host/frame abstraction with title, icon, close/hide action, detach/attach action, and drag handle. Keep docking mechanics isolated from content panels. If a third-party docking package is not already available, implement the first version with LCL panels and separate forms, while keeping the host API ready for a real docking manager later.
- `uNavigationPanel.pas`: navigation rail and navigation content implementation. Use one shared item definition to generate buttons/tooltips and avoid repeated event handlers.
- `uChatPanel.pas`: chat history/empty state, workspace label, multiline prompt editor, mode selector, model selector, attachment/context affordances, and send action. The send action should initially validate/forward the prompt through an event/callback rather than implement the AI backend.
- `uMainWorkspace.pas`: main form composition, menu/toolbar/status bar, panel registration, layout commands, theme switching, and coordination with `TWorkspaceState`.

Update `mainunit.pas`/`.lfm` only enough to host or inherit from the new workspace form, and update `lazycodingagent.lpi` to include every new unit. Do not put the complete UI construction and all event logic into `mainunit.pas`.

## Main menu

Create these top-level menus:

- **File**: New workspace, Open workspace/project, Close workspace, Exit
- **View**: Show/hide panel submenu, Reset layout, Toggle toolbar, Toggle status bar, Toggle light/dark theme
- **Window**: list all registered panels with checked visibility state; Dock/Attach current panel; Detach current panel; Reset all windows
- **Workspace**: Home, Projects, Sessions, Bots, selected workspace/project actions
- **Agent**: Ask, Plan, Agent, model selection, settings/context actions
- **Help**: About and keyboard-shortcut reference

The Window menu must be generated from the panel registry/state, not duplicated manually. Visibility changes from the menu, panel close buttons, and toolbar layout buttons must all call the same state/controller methods.

## Toolbar

Use a compact modern toolbar below the menu with grouped actions:

- Workspace: New, Open, Save
- Navigation: Home, Projects, Sessions, Bots
- Layout: Window/panel chooser, Reset layout
- Agent: current mode, selected model, Send/Run affordance
- Appearance: theme toggle and settings

Use short captions where space allows, icons plus tooltips for compact actions, and avoid platform-specific glyph assumptions. Use LCL-safe image lists/resources or text fallback if an icon set is not available. Do not make toolbar buttons the only route to important commands; menus and keyboard shortcuts should remain available.

## Detachable and rearrangeable windows

- Define a registry for panels with stable ID, title, default dock side, minimum size, visibility, and detach capability.
- Default startup arrangement: navigation rail/content and chat docked to the main form; secondary panel registered but hidden or collapsed according to the chosen empty-state design.
- A detached panel should be hosted in a border-aware child `TForm`, preserve its panel identity, and be movable to another monitor using normal LCL window behavior. On reattach, return the content to its dock host without creating duplicate panel instances.
- Add a drag handle/title bar to docked panel headers and define drop targets between the primary columns. Persist panel order, visibility, and detached bounds only after the basic behavior is reliable.
- Guard detached forms on application shutdown and workspace reset. Restore the main form if a user closes a detached panel rather than losing its state.
- Keep docking implementation behind an interface/controller so a later docking component can replace the first implementation without changing chat or navigation panels.

## Chat behavior and visual details

- Start in the empty state and show the project/workspace placeholder in the heading.
- The composer is multiline, supports Enter/Shift+Enter behavior documented by tooltip/help, and has a clear send button.
- Mode buttons are mutually exclusive and visually distinguish selected state; default mode is `Agent`.
- Model selector displays the selected model and supports a future model registry; use a placeholder model such as `Default model` until backend configuration exists. Do not pretend a model is connected when it is not.
- Keep message history and agent execution as separate future services. For this layout task, provide empty history state and a prompt-submitted event.
- Add keyboard focus order: navigation rail -> panel content -> chat history -> composer -> mode/model controls -> send.
- Use minimum sizes and proportional layout behavior so the chat area remains usable on small screens; for narrow windows collapse/hide optional panels rather than forcing clipped controls.

## Cross-platform and theme requirements

- Use standard LCL controls, `TForm`, `TPanel`, `TSplitter`, `TMenuItem`, `TToolBar`/buttons, `TPageControl` where appropriate, and platform-neutral APIs.
- Avoid Windows-only APIs, hard-coded title-bar behavior, system tray assumptions, or platform-specific path separators.
- Use DPI-aware dimensions and scale spacing/icons through LCL scaling. Test high-DPI behavior and multiple monitor movement on Windows, Linux, and macOS widgetsets.
- Dark theme is the default; light theme must use the same semantic color tokens. Check text contrast, selected states, disabled states, focus rectangles, and splitter visibility in both themes.
- Keep detachable window bounds validated against available screens so a panel is not restored entirely off-screen.

## Persistence and state

Add a small layout/settings persistence service after the in-memory behavior works. Store theme, selected mode/model, panel visibility/order, docking state, and detached bounds in a user configuration location using portable RTL/LCL mechanisms. Treat corrupt or unavailable settings as recoverable: fall back to defaults and continue startup. Do not store project-specific secrets in layout settings.

## README update

Because the repository rule requires README updates for new features, add a UI/layout section documenting:

- The main menu, toolbar, navigation rail, chat workspace, and reserved panel
- Agent as the default mode and the Ask/Plan alternatives
- Panel show/hide, drag rearrangement, docking, and detachment across monitors
- Dark/light theme support and cross-platform intent

## Verification checklist

1. Open the project in Lazarus and verify all new units are included in the `.lpi`.
2. Build for at least the available target and inspect compiler diagnostics; resolve warnings caused by unused or platform-specific units.
3. Confirm startup defaults: dark theme, Agent mode, chat empty state, navigation visible, secondary panel reserved, and chat workspace visible.
4. Confirm each rail icon has a tooltip and selecting it updates the navigation content and selected state.
5. Confirm Window menu checkmarks remain synchronized when panels are hidden, shown, detached, reattached, or closed.
6. Drag/rearrange docked panels and verify the chat panel remains usable after resizing.
7. Detach a panel, move it to another monitor/screen, close it, reattach it, and restart to verify safe bounds/state recovery.
8. Switch Ask/Plan/Agent and model selection; verify Agent is restored as the default when no preference exists.
9. Switch dark/light themes and inspect contrast, focus, hover, disabled, menu, toolbar, detached-form, and status-bar states.
10. Exercise keyboard navigation and basic narrow-window behavior.
11. Update README and review the final Git diff to ensure only intended source, form, project, and documentation files changed.

## Suggested implementation order

1. Add shared types, state, theme tokens, and panel registry interfaces.
2. Build the main form shell with menu, toolbar, status bar, and three-column docking placeholders.
3. Implement navigation rail/content and tooltips.
4. Implement chat empty state and composer controls with Agent as default.
5. Implement panel visibility commands and generated Window menu.
6. Add docking/detachment/rearrangement behavior and safe lifecycle handling.
7. Add theme switching, persistence, and responsive sizing.
8. Update project metadata and README.
9. Build, inspect diagnostics, and run the verification checklist.
