# Implementation Plan: Fix `TControl.ChangeBounds` Loop for `TComboBox`

## Diagnosis

The reported loop is most directly explained by the chat composer layout repeatedly assigning a combo-box height that the LCL/native widget changes during bounds negotiation:

- `uChatPanel.pas:288-289` calls `SetBoundsIfChanged(..., Top=2, Height=28)` for `FModeCombo` and `FModelCombo`.
- `uTheme.pas:118-119`, called from `TChatPanel.ApplyTheme`, changes the same controls to `csOwnerDrawFixed` and sets `ItemHeight := 22`.
- The native/LCL combo reports a preferred control height of approximately 24px and can normalize the requested 28px to 24px (or otherwise re-enter bounds calculation). The diagnostic's `NewHeight=28` with an unchanged `Left/Top/Width` is consistent with the manual layout and native preferred-height negotiation fighting each other.
- The existing `SetBoundsIfChanged` only compares the exposed `Height`; it does not protect against re-entrant layout and does not establish a single source of truth for combo sizing.

There is also a similar potential conflict in `frmSettings.lfm`, where `cboProvider` is streamed with `Height = 23`, then `StyleComboBox` changes owner-draw/item metrics at runtime. The fix should therefore centralize combo metrics and avoid setting incompatible item/control heights.

## Scope

Do not change the detachable-window architecture or replace visual-designer forms. Keep the fix LCL-based and cross-platform for Windows, Linux, and macOS.

### 1. Centralize safe combo-box metrics in `uTheme.pas`

- Add a shared combo control-height constant/helper, or an equivalent single routine, so all themed combos use the same intended control height and item height.
- In `StyleComboBox`, configure the style and item height before applying the final control bounds; avoid forcing a control height from the theme routine if the caller owns layout height, or explicitly use one consistent height everywhere.
- Preserve owner drawing, palette colors, font setup, and invalidation behavior.
- Ensure styling is idempotent: repeated theme application must not cause repeated geometry changes or trigger a bounds feedback cycle.
- Review `ApplyControlTheme`/platform scrollable-theme traversal so combo styling is not indirectly re-applied with conflicting metrics during the same layout pass. Keep native Windows theme handling intact, including the owner-draw exception.

### 2. Make chat layout the sole owner of combo bounds in `uChatPanel.pas`

- Update `UpdateLayout` so `FModeCombo` and `FModelCombo` receive one stable, platform-safe height that matches the centralized combo metrics; keep their explicit top offset/spacing and horizontal positions.
- Continue using `SetBoundsIfChanged`, but add a small re-entrancy guard around `UpdateLayout` (for example, an `FUpdatingLayout` field with `try/finally`) so a native `ChangeBounds`/resize callback cannot recursively execute the same manual layout.
- Apply the guard to all early/exception paths and preserve the existing `Resize`, constructor, and running-state behavior.
- Avoid setting `Align`/`BorderSpacing` on these manually positioned controls unless the implementation removes manual `SetBounds`; do not mix two layout owners. This is important because the previous alignment/margins approach can still compete with explicit `SetBounds`.
- Keep button and combo vertical alignment visually consistent in the 32px footer without introducing hardcoded platform-specific widget hacks.

### 3. Align settings-form combo metrics

- Update `frmSettings.lfm` only as needed so `cboProvider` starts with the same safe design-time height/owner-draw-compatible metrics used at runtime.
- Keep the visual designer as the source of the dialog’s static layout and retain the existing `OnDrawItem` hookup and theme application.
- Ensure `ApplyTheme` does not cause the streamed height and themed item height to oscillate.

### 4. Documentation

- Update `README.md` in the UI/design section with a concise note that themed combo boxes use stable, centralized LCL metrics and guarded layout, preventing bounds-loop warnings across supported platforms.
- Do not document an implementation-specific workaround as a user-facing feature; describe the resulting stability/cross-platform polish.

## Verification Plan

1. Build the Lazarus project using the project’s `.lpi` target and inspect diagnostics for new compiler errors/warnings.
2. Run the application with the default dark theme and open the chat composer. Confirm both mode/model combos render at a stable height beside the action buttons and no `TControl.ChangeBounds loop detected` message appears during startup, resize, theme application, or model refresh.
3. Toggle dark/light mode repeatedly and resize the main window across minimum and ordinary widths. Confirm combo bounds settle after one layout pass and the footer remains aligned.
4. Open Settings, switch provider/theme, and close/reopen the dialog. Confirm `cboProvider` remains stable and owner-drawn without bounds warnings.
5. Exercise detached panels and move them between monitors; confirm the combo fix does not alter docking/floating behavior.
6. Repeat the checks on Windows, Linux, and macOS LCL backends where available, because native combo preferred heights differ by widgetset.

## Files Expected to Change

- `uTheme.pas` — centralized, idempotent combo metrics and theme application.
- `uChatPanel.pas` — guarded manual layout and stable combo bounds.
- `frmSettings.lfm` and/or `frmSettings.pas` — align design-time/runtime combo metrics if required.
- `README.md` — document the cross-platform UI stability refinement.

No implementation is included in this plan.
